# rfq-mm — a quote-driven RFQ market-making simulator

[![CI](https://github.com/OWNER/rfq-market-maker/actions/workflows/ci.yml/badge.svg)](https://github.com/OWNER/rfq-market-maker/actions/workflows/ci.yml)

## What this is

A research simulator of a quote-driven market-making desk on a reference-market-anchored
RFQ venue, with the venue's rules expressed as configuration rather than hardcoded logic.
It is modelled on the **European Investor Exchange (EIX)** market-maker regime — a
quote-driven venue anchored to a reference market (Xetra, for German names), *not* a
central limit order book. Given a request for a quote, the simulated market maker prices
it (Avellaneda–Stoikov inventory skew + a regulatory spread cap), decides whether to
answer or claim an exemption, and tracks every §5/§7/§8/§12/§15 obligation from the venue's
public rulebook as it goes.

**Every data path in this project is a documented proxy.** There is no real EIX market
data, no EIX connectivity, and no way to get either — EIX publishes no public market-data
API, and Xetra's real-time L1 feed is a paid, licensed product. Overclaiming here would be
the fastest way to fail a quant screen, so before anything else:

## What is real

- The venue rulebook: **Regelwerk European Investor Exchange, 09.12.2024** (cited by
  section throughout `venues/eix.yaml` and the code that implements it), and the second
  venue config, **Börse München's "Ausführungsbestimmungen der Geschäftsführung zum
  Regelwerk der Börse München", Stand 17.01.2025** (`venues/gettex.yaml`) — both public
  documents, not reproductions of any proprietary system.
- The tick-size regime: MiFID II **RTS 11** (Commission Delegated Regulation (EU)
  2017/588), cross-checked against three independent published reproductions of the
  Annex table (see `src/rfq_mm/core/ticks.py`'s module docstring for the citations).
- In `bars` feed mode, the underlying price series is real: `yfinance` 1-minute bars for
  the named German/European ticker.

## What is simulated

- **All RFQ flow** — arrival times, sizes, direction, and the "informed fraction" label
  are generated by `flow/generator.py` (a non-homogeneous Poisson process with log-normal
  sizes). No public dataset of retail RFQ arrivals exists to calibrate this against.
- **The bid/ask spread in `bars` mode** — real 1-minute bars carry no bid/ask, so the
  spread is *estimated* per bar-pair via the Corwin–Schultz (2012) high-low estimator,
  not invented as a fixed number.
- **All fills** — the client-acceptance decision (`engine/rfq.py::decide_acceptance`) is a
  documented probabilistic proxy for real client behaviour.
- **The entire order book in `synthetic` mode** — a geometric Brownian motion mid-price
  with U-shaped intraday volatility seasonality, deterministic from a seed. This is a
  feature, not a compromise: with synthetic data the true fair value is known exactly, so
  the informed-fraction parameter can be *validated* — inject a known φ, then check the
  markout curve recovers it (see `notebooks/01_results.ipynb`).

## What this is not

Not connected to EIX, not a latency-sensitive production trading gateway (it is a
`heapq`-based research simulator — no C++/Rust "for speed"), not affiliated with or
endorsed by Scalable Capital, mwb fairtrade, Baader Bank, BÖAG Börsen AG, or Bayerische
Börse AG, and not a reproduction of any proprietary system. Built entirely from public
regulatory documents.

## What I would do differently with real data

- Calibrate the arrival intensity and informed fraction against actual RFQ logs instead
  of an assumed non-homogeneous Poisson process.
- Use real L1 order-book depth for the size-aware §7(1) spread cap, instead of the
  synthetic feed's depth model or the `bars` tier's Corwin–Schultz estimate.
- Measure the §8(2) withdrawal rate against real quote-to-acceptance latencies, instead of
  the documented client-acceptance proxy.

## Setup

```bash
# 1. Install uv (https://docs.astral.sh/uv/getting-started/installation/)
curl -LsSf https://astral.sh/uv/install.sh | sh

# 2. Install Python 3.12 and sync dependencies
uv python install 3.12
uv sync --all-groups

# 3. Validate a venue config
uv run mm validate venues/eix.yaml
```

If `uv` is unavailable, a generated `requirements.txt` is committed as a fallback:
`pip install -r requirements.txt` into a Python 3.12 virtualenv, then run commands as
`python -m rfq_mm.cli ...` instead of `uv run mm ...`.

### `mm report` needs two extra system-level pieces

`mm report`'s PDF output uses **weasyprint**, which needs Pango/Cairo/GDK-Pixbuf, and
**kaleido**, which needs a headless Chrome. Neither is a Python package alone:

```bash
# macOS
brew install pango
uv run plotly_get_chrome -y   # downloads a headless Chrome for kaleido

# then, every time you run `mm report` on macOS (weasyprint needs this to find
# the libraries Homebrew installed to a non-default path):
DYLD_LIBRARY_PATH=/opt/homebrew/lib uv run mm report ...
```

```bash
# Debian/Ubuntu (what CI uses)
sudo apt-get install -y libpango-1.0-0 libpangocairo-1.0-0 libgdk-pixbuf2.0-0 libffi-dev
uv run plotly_get_chrome -y
```

**Known issue:** kaleido's v1.x headless-Chrome backend has been intermittently flaky in
this project's own development environment — the identical export call sometimes fails
with `BrowserFailedError` and sometimes succeeds, with nothing else different. `mm report`
isolates each chart export in its own subprocess and retries a few times, which helps but
doesn't eliminate it entirely. If it fails, retrying the command (or closing other
Chrome/Chromium processes first) has always resolved it in testing. This does not affect
`mm run`, `mm sweep`, `mm audit export`, or the interactive HTML half of `mm report`'s
output (which needs only Plotly.js via CDN, not kaleido) — only the static PDF export path.

## CLI

| Command | Does |
|---|---|
| `mm validate <venue>` | Validate and pretty-print a venue rulebook |
| `mm run <venue> --date YYYY-MM-DD` | Run one simulated day end-to-end; writes fills/quotes/audit to `--out-dir` and prints a compliance + P&L summary |
| `mm report <venue> --date YYYY-MM-DD` | Run one simulated day and emit a self-contained interactive HTML + PDF desk report to `--report-dir` |
| `mm sweep <venue> --date YYYY-MM-DD` | γ × φ × inventory-limit sensitivity grid, written to CSV |
| `mm audit export --input a.jsonl --output a.parquet` | Export a recorded audit trail (§16) |

Run `mm <command> --help` for the full option list (feed tier, seed, γ, informed fraction,
inventory limit, ISIN list, ...).

### Examples

```bash
# Validate both venue configs
uv run mm validate venues/eix.yaml
uv run mm validate venues/gettex.yaml

# Run one day on EIX, synthetic feed, six DAX names + two ETFs (the default universe)
uv run mm run venues/eix.yaml --date 2026-09-07

# Run on real SAP.DE 1-minute bars instead
uv run mm run venues/eix.yaml --isins DE0007164600 --date 2026-09-09 --feed bars

# Same command, second venue — proves the schema generalizes
uv run mm run venues/gettex.yaml --date 2026-09-07

# Sensitivity grid
uv run mm sweep venues/eix.yaml --isin DE0007164600 --date 2026-09-07 \
  --gammas 0.002,0.005,0.01 --phis 0.0,0.1,0.3 --inventory-limits 100000,300000
```

## Repository layout

```
venues/               # venue rulebooks as YAML config (eix.yaml, gettex.yaml)
src/rfq_mm/
  core/                # types, session calendar, RTS 11 ticks — no venue-specific code
  venue/               # Pydantic rulebook schema, §5 obligations, §7 guarantees
  feed/                # synthetic (GBM), bars (yfinance + Corwin-Schultz)
  flow/                # RFQ arrival/size/side/informed-fraction generator
  instruments/         # curated instrument fixture (segments, tickers, start prices)
  engine/               # quoting (§5), TTL/withdrawal/firm-size (§8), day orchestrator
  risk/                # inventory limits + kill switch, hedger
  compliance/          # response-ratio/breach monitor, §12 surveillance, §15 audit log
  analytics/           # markouts, P&L attribution, sweep grid
  report/              # Jinja2 + weasyprint desk report
  cli.py               # mm validate | run | report | sweep | audit export
tests/                 # unit, property (Hypothesis), integration
notebooks/01_results.ipynb
reports/                # committed desk_report_YYYY-MM-DD.pdf
docs/                   # committed 2-page application summary PDF
```

## Portability

Retargeting to another venue is a config change, at most one feed adapter — see
`venues/README.md` for how to add one. This project already ships two:

- **`gettex`** (Baader Bank as market maker, operated by Bayerische Börse AG) — same
  quote-driven German venue model, different reference market/volume tables, researched
  from Börse München's own public rulebook (see `venues/gettex.yaml`'s header for exactly
  which figures are sourced vs. flagged as schema-generality gaps).
- Retargeting to **Tradegate**, **Lang & Schwarz**, or **mwb fairtrade** would follow the
  same pattern.
- Retargeting to a **crypto broker** (Bitpanda, Bison) would drop the rulebook module
  entirely and keep the inventory/adverse-selection/markout machinery unchanged — the
  spread policy becomes an internal risk decision rather than a regulatory one.
- Retargeting to a **broker-side / best-execution** use case inverts the question: instead
  of "is my quote profitable?", ask "were our clients' fills competitive against the
  reference venue?" — same fill and reference-market data, same code, a different report
  template.

## Explicitly out of scope

No matching engine (EIX is not a CLOB — see "What this is"). No ML models. No C++/Rust
"for speed" — this is a research simulator, not a latency-sensitive gateway. No live
broker connectivity. No scraping of EIX, Börse Hannover, Bayerische Börse, or Scalable
pages.
